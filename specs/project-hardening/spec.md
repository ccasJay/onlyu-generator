# 项目可靠性加固 Spec（P0–P2）

## 目标与范围

本规范覆盖项目分析中 P0–P2 的工程修复，目标是让这个桌面海报生成器在真实使用中不丢内容、导出可预期、离线可用、可安全升级，并具备可持续维护的工程基线。用户价值是：关闭应用后草稿仍在；照片和表单输入不会因过大或非法而卡死；导出在 Tauri 与浏览器两条通道都有明确结果；海报在内容达到上限时仍不溢出；Windows 用户能收到签名校验后的自动更新。

**范围内：**

- 草稿与照片的本地自动保存、恢复、重置与按模板隔离。
- 图片类型/大小校验、透明通道保留的压缩与导出前校验。
- 必填校验、字段长度/数量上限、标签与亮点输入规范化。
- Tauri 原生保存对话框 + 浏览器下载回退的双通道导出。
- 模板初始化、字段补齐、切换与重置逻辑重构。
- 海报长文本自适应、窗口尺寸调整、模板样式作用域隔离。
- 移除 Google Fonts 远程依赖，改用系统字体栈。
- 错误边界、可访问性基础、ESLint/Prettier/Vitest/Playwright 与 README。
- 版本统一、PR CI、Windows NSIS 发布、公开仓库直接发布与自动更新。

**范围外（Non-goals）：**

- 联系方式/微信二维码字段、模板选择器 UI、照片拖拽/缩放、批量生成、历史记录、云同步。
- macOS/Linux 安装包发布、Windows 代码签名证书、更新回滚、遥测/崩溃上报。
- 海报视觉重设计或品牌色调整；本次只做可靠性与排版约束，不改变既有视觉方向。
- 多用户、账号体系或任何服务端业务接口。

## 需求与验收标准

### 需求 1：草稿自动保存与恢复

作为海报制作者，我希望编辑内容在关闭应用后仍能恢复，以便避免重复录入。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当应用启动且存在当前模板的有效草稿时，系统应当恢复模板、全部字段和照片，并在 1 秒内呈现；恢复完成前不得用默认值覆盖或持久化表单。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当表单内容发生变化时，系统应当在 1 秒内将草稿写入本地存储，并在表单区显示“保存中 / 已保存 / 保存失败”的非阻塞状态。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当应用在保存后关闭并重新打开时，系统应当恢复最后一次成功保存的内容；允许最多丢失关闭前 1 秒内尚未完成的输入。
- <a id="spec-req-1-4"></a>**验收标准 1.4**：若不存在草稿、草稿损坏或 schema 版本不受支持，系统应当使用模板默认值启动并保持可用；仅在损坏或不支持时显示一次非阻塞提示，不得崩溃或阻塞编辑。
- <a id="spec-req-1-5"></a>**验收标准 1.5**：若 IndexedDB 不可用或配额不足，系统应当保持当前内存数据可编辑并显示非阻塞警告，在条件恢复后继续尝试保存；不得清空表单或删除已有草稿。
- <a id="spec-req-1-6"></a>**验收标准 1.6**：系统应当仅在本机保存草稿和照片，不得发起任何草稿或照片上传请求。

### 需求 2：图片上传校验与压缩

作为海报制作者，我希望上传的照片自动适配海报尺寸，以便避免卡顿、超大文件和导出失败。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当用户选择 JPG、PNG 或 WebP 且原文件不超过 20MB 时，系统应当将最长边压缩到不超过 2000px、保留透明通道、优先输出 WebP（质量约 0.92），并生成不超过 8MB 的本地图片数据；处理期间显示加载态。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：若压缩结果仍超过 8MB，系统应当以最长边 1600px、质量 0.88 重试一次；仍超限时拒绝该图片并保留原照片。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：若文件类型不支持、原文件超过 20MB、图片解码失败或读取失败，系统应当显示具体中文错误并保留原照片，不得写入半成品数据。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当用户清除照片时，系统应当移除预览和草稿中的照片，并持久化该状态。
- <a id="spec-req-2-5"></a>**验收标准 2.5**：图片处理期间系统应当禁止导出，避免导出旧图或不完整图。
- <a id="spec-req-2-6"></a>**验收标准 2.6**：系统不得将照片上传到任何网络位置。

### 需求 3：表单约束与导出校验

作为海报制作者，我希望在导出前发现缺失或超限内容，以便得到可用的成品而不是溢出的海报。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当用户点击导出时，系统应当校验所有 `required` 字段；本版必填项为照片和姓名。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：若必填项缺失，系统应当阻止导出，聚焦第一个错误字段并显示字段级中文错误；修正后错误应当消失。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：系统应当按字段元数据限制输入：城市 6 字、职位 8 字、姓名 8 字、薪资 16 字、标签最多 8 个且每个最多 6 字、亮点最多 4 条且每条最多 24 字、通用文本域最多 200 字；达到上限后阻止继续输入并显示上限提示。
- <a id="spec-req-3-4"></a>**验收标准 3.4**：当添加标签或亮点时，系统应当去除首尾空白、忽略空项，并对标签去重。
- <a id="spec-req-3-5"></a>**验收标准 3.5**：若字段只包含空白字符，系统应当视为空值，并按必填规则处理。
- <a id="spec-req-3-6"></a>**验收标准 3.6**：当所有校验通过时，系统应当允许导出，并继续执行需求 4 的导出流程。

### 需求 4：可靠的双通道导出

作为海报制作者，我希望导出在桌面端和浏览器预览中都能稳定完成，以便明确知道文件保存到了哪里。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当在 Tauri 环境中导出且校验通过时，系统应当等待字体和照片加载完成，生成 1800×2668 的 PNG（当前 900×1334 模板的 2 倍），打开原生保存对话框，并使用默认文件名 `<姓名>_<YYYY-MM-DD>.png`。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：若用户取消保存，系统应当不写文件、不显示错误，并恢复可导出状态。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：当在浏览器模式导出时，系统应当使用相同的校验、渲染和命名规则，通过浏览器下载保存。
- <a id="spec-req-4-4"></a>**验收标准 4.4**：若文件写入失败，系统应当显示可重试的中文错误，不得留下半截文件或破坏已存在的同名文件，并保留全部表单数据。
- <a id="spec-req-4-5"></a>**验收标准 4.5**：系统应当清理文件名中的非法字符，将空名称回退为“海报”，并将文件名主体限制在 80 个字符以内。
- <a id="spec-req-4-6"></a>**验收标准 4.6**：系统应当禁止并发导出；导出期间按钮显示进行中状态并禁用重复触发。
- <a id="spec-req-4-7"></a>**验收标准 4.7**：若照片或字体加载失败，系统应当阻止导出并提示具体原因，不得导出占位图或缺失内容的图片。
- <a id="spec-req-4-8"></a>**验收标准 4.8**：导出结果应当与预览使用同一模板 DOM 和内容，预览缩放比例不得影响输出尺寸或内容。

### 需求 5：模板初始化、重置与切换

作为后续模板的维护者，我希望模板生命周期有唯一入口，以便新增模板时不会出现字段残留或默认值缺失。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当首次启动且无草稿时，系统应当仅初始化一次模板默认值，不得因重复 effect 产生重复写入或覆盖用户输入。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：当恢复的草稿缺少模板新增字段时，系统应当用该字段默认值补齐，同时保留草稿中已有值。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当用户确认重置时，系统应当删除当前模板的草稿和照片并立即恢复默认值；取消时不得修改任何内容；其他模板的草稿不受影响。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当切换模板时，系统应当先保存当前模板草稿，再加载目标模板草稿；目标模板无草稿时使用其默认值；不得出现字段跨模板残留。
- <a id="spec-req-5-5"></a>**验收标准 5.5**：若模板 ID 不存在，系统应当保留当前模板并显示非阻塞警告，不得崩溃或清空表单。

### 需求 6：排版约束与窗口适配

作为海报制作者，我希望在字段上限内输入任意内容都不会破坏版式，以便预览和导出结果一致。

- <a id="spec-req-6-1"></a>**验收标准 6.1**：当应用以默认尺寸启动时，窗口应当为 1280×860；最小尺寸应当为 1100×760，并且在最小尺寸下不出现横向滚动，预览区仍完整可见。
- <a id="spec-req-6-2"></a>**验收标准 6.2**：当所有字段达到验收标准 3.3 的上限时，预览和导出中不得出现文字溢出海报、遮挡照片、越过信息卡片边界或覆盖品牌落款的情况。
- <a id="spec-req-6-3"></a>**验收标准 6.3**：当职位、姓名、薪资或亮点较长时，系统应当按长度分级缩小字号；标签应当保持在左列宽度内；亮点应当在卡片内换行且不改变卡片可读性。
- <a id="spec-req-6-4"></a>**验收标准 6.4**：模板 CSS 变量和选择器应当限定在模板根节点内，不得影响应用框架或其他模板。
- <a id="spec-req-6-5"></a>**验收标准 6.5**：系统应当移除 Google Fonts 远程 `@import`，改用系统字体栈；离线状态下编辑和导出不得依赖任何远程字体请求。
- <a id="spec-req-6-6"></a>**验收标准 6.6**：若系统字体缺失或回退到通用 `sans-serif`，验收标准 6.2 的不得溢出约束仍然成立。
- <a id="spec-req-6-7"></a>**验收标准 6.7**：预览缩放应当根据可用视口计算，海报基准尺寸保持 900×1334，不得因窗口缩放改变导出尺寸。

### 需求 7：异常兜底与可访问性

作为使用者，我希望应用出错时仍能恢复操作，并能通过键盘和辅助技术完成主要流程。

- <a id="spec-req-7-1"></a>**验收标准 7.1**：当 React 渲染发生未捕获错误时，系统应当显示错误边界兜底页，提供“重新加载”和“清除当前草稿并重新加载”（需二次确认）操作，不得只显示白屏。
- <a id="spec-req-7-2"></a>**验收标准 7.2**：所有用户可见错误应当通过字段级提示、页面内提示或原生对话框呈现；不得仅写入控制台。
- <a id="spec-req-7-3"></a>**验收标准 7.3**：表单标签应当与输入控件关联；仅图标按钮应当有可读的 `aria-label`；标签删除、亮点删除、重置、导出和检查更新均可通过键盘操作。
- <a id="spec-req-7-4"></a>**验收标准 7.4**：重置、覆盖保存、清除草稿和安装更新等破坏性或不可逆操作，系统应当要求用户明确确认，且确认对话框可取消。
- <a id="spec-req-7-5"></a>**验收标准 7.5**：所有可交互控件应当有可见的键盘焦点样式，不得依赖颜色作为唯一状态提示。

### 需求 8：工程质量与自动化验证

作为维护者，我希望关键逻辑有自动化回归保护，以便后续增加模板或发布更新时敢于改动。

- <a id="spec-req-8-1"></a>**验收标准 8.1**：项目应当提供并通过 `lint`、`format:check`、`typecheck`、`test`、`build` 脚本；`lint` 不得有错误，且不得保留无理由的 `eslint-disable`。
- <a id="spec-req-8-2"></a>**验收标准 8.2**：PR CI 应当在 Ubuntu 上使用 `npm ci` 执行 lint、typecheck、test 和 build；涉及 `src-tauri` 的变更还应当在 Windows 上执行 `cargo check`。任一检查失败时 PR 不得被视为通过。
- <a id="spec-req-8-3"></a>**验收标准 8.3**：自动化测试应当覆盖草稿恢复/损坏/配额异常、图片压缩与透明通道、表单校验、模板初始化/重置/切换、文本上限排版，以及表单错误与导出阻断的组件行为。
- <a id="spec-req-8-4"></a>**验收标准 8.4**：浏览器端 Playwright 冒烟测试应当覆盖应用加载、填写字段、实时预览、必填校验和浏览器下载导出。
- <a id="spec-req-8-5"></a>**验收标准 8.5**：原生保存、更新检查/安装等 Tauri 专属流程应当有书面手工验证清单；自动化测试不得依赖真实网络或真实更新源。
- <a id="spec-req-8-6"></a>**验收标准 8.6**：README 应当记录开发、构建、测试、发布、更新签名密钥与 CI secrets 的配置步骤，以及手工验证清单。
- <a id="spec-req-8-7"></a>**验收标准 8.7**：组件应当只订阅所需状态；单个字段变化不得触发与它无关的区域无意义重渲染；标签、亮点等动态列表应当使用稳定标识，删除中间项后不得出现内容错位或错误复用。

### 需求 9：版本统一与 Windows 发布

作为发布者，我希望版本、标签和发布产物保持一致，以便用户和更新器能正确识别新版本。

- <a id="spec-req-9-1"></a>**验收标准 9.1**：`package.json`、`package-lock.json` 根版本、`src-tauri/tauri.conf.json` 和 `src-tauri/Cargo.toml` 的版本应当统一为 `0.2.0`；CI 应当提供并执行版本一致性检查。
- <a id="spec-req-9-2"></a>**验收标准 9.2**：发布标签应当采用 `v0.2.0` 格式，发布标题应当为 `OnlyU Generator v0.2.0`；标签版本与任一版本源不一致时，发布流程应当在构建前失败。
- <a id="spec-req-9-3"></a>**验收标准 9.3**：发布流程应当只构建 Windows NSIS 安装包，启用 updater 产物生成，使用 `npm ci`，缓存 npm/Rust 依赖，并设置并发控制避免同一版本重复发布。
- <a id="spec-req-9-4"></a>**验收标准 9.4**：发布流程应当将安装包、签名文件和 `latest.json` 发布到当前公开源码仓库的 Release；仓库和 Release 中不得包含签名私钥。
- <a id="spec-req-9-5"></a>**验收标准 9.5**：若签名私钥或密码缺失，发布流程应当失败并且不得发布未签名产物。
- <a id="spec-req-9-6"></a>**验收标准 9.6**：首个启用自动更新的版本发布说明应当明确：`0.1.0` 用户需要手动安装一次 `0.2.0`，自动更新从 `0.2.0` 起生效。

### 需求 10：签名自动更新

作为 Windows 用户，我希望应用在启动时静默检查并安全安装新版本，以便及时获得修复而不必手动下载。

- <a id="spec-req-10-1"></a>**验收标准 10.1**：当 Tauri 应用启动并完成初始化后，系统应当在后台静默检查更新；无更新或检查失败时不显示打扰性提示，每次启动最多检查一次。
- <a id="spec-req-10-2"></a>**验收标准 10.2**：顶栏应当提供“检查更新”入口；检查中显示进行中状态；无更新时提示“已是最新版本”；有更新时展示当前版本、最新版本和纯文本更新说明，并提供“下载并安装”和“稍后”两个选择。
- <a id="spec-req-10-3"></a>**验收标准 10.3**：下载安装期间系统应当显示进度或进行中状态；失败时显示可重试的中文错误，应用保持可用，不得影响当前草稿。
- <a id="spec-req-10-4"></a>**验收标准 10.4**：系统应当只从配置的 HTTPS 更新源获取更新，并验证 Tauri updater 签名；签名无效、来源不可信或版本低于当前版本时应当拒绝安装并提示错误。
- <a id="spec-req-10-5"></a>**验收标准 10.5**：安装完成后系统应当提示重启；用户确认后重启应用，拒绝时应用继续运行。
- <a id="spec-req-10-6"></a>**验收标准 10.6**：在非 Tauri 环境中系统应当隐藏检查更新入口并且不发起更新请求，不得报错。
- <a id="spec-req-10-7"></a>**验收标准 10.7**：应用更新不得改变 Tauri identifier，更新后应当保留 IndexedDB 中的草稿和照片。
- <a id="spec-req-10-8"></a>**验收标准 10.8**：更新签名私钥只能存在于 CI secrets，不得提交到仓库、写入日志或打包进产物；应用内只包含公钥。
- <a id="spec-req-10-9"></a>**验收标准 10.9**：更新源应当为当前公开源码仓库的 `latest.json`，客户端无需认证即可访问；`latest.json` 中的安装包 URL 必须指向同一公开仓库资产。
- <a id="spec-req-10-10"></a>**验收标准 10.10**：启动检查失败或超过 15 秒未完成时应当静默结束；手动检查超时应当显示可重试错误，不得阻塞编辑或导出。
- <a id="spec-req-10-11"></a>**验收标准 10.11**：更新说明应当以纯文本呈现，不得将远端 HTML 注入页面。

## 架构与核心决策

### 系统拓扑与接口

React SPA 与 Tauri 壳的职责边界保持不变，新增四个内部边界：`draft repository`（IndexedDB 持久化）、`platform bridge`（Tauri/浏览器能力探测与保存）、`image pipeline`（校验、压缩、解码）、`update service`（检查、下载、安装）。表单、预览、导出仍以模板定义和同一个 `formData` 为唯一数据源。

**启动与恢复。** Store 增加 `hydrationStatus: loading | ready | degraded`。应用启动时先读取持久化的 `currentTemplateId` 与对应草稿，完成前只渲染加载态，不初始化默认值、不写回存储。恢复完成后补齐新增字段并进入 `ready`；读取失败进入 `degraded`，使用默认值并允许编辑。这样避免异步恢复与旧 effect 初始化互相覆盖。

**草稿存储。** IndexedDB 使用两个对象仓库：`drafts` 以 `templateId` 为主键，保存 `schemaVersion`、模板 ID、除照片外的字段、`photoId` 和 `updatedAt`；`images` 以 `photoId` 为主键，保存压缩后的图片数据与时间。文本变化只重写较小的 `drafts` 记录，照片单独写入，避免每次按键重写大图。恢复时合并模板默认值与草稿字段；重置时同时删除当前模板的 `drafts` 与关联 `images`；启动时可清理无引用的图片记录。

**导出接口。** `exportPoster()` 统一执行：校验 → 等待 `document.fonts.ready` 与照片解码 → 用 `html-to-image` 以 2 倍像素比渲染 → 调用 `savePng(dataUrl, filename)`。`savePng` 在 Tauri 环境通过 dialog 插件选择路径，并调用一个窄职责 Rust 命令写入；浏览器环境回退 `file-saver`。Rust 命令先写同目录临时文件，完整写入后再替换目标，避免半截文件。不引入 `fs` 插件的宽泛路径权限。

**更新接口。** `update service` 仅在 Tauri 环境启用，封装 `check()`、`downloadAndInstall()`、`relaunch()`，向 UI 暴露 `idle | checking | available | downloading | ready | error` 状态。启动检查在应用进入 `ready` 后延迟触发；手动入口复用同一服务。更新说明按纯文本渲染。

**安全配置。** 生产 CSP 收紧为仅允许本地脚本/样式、`data:`/`blob:` 图片和 Tauri IPC，禁止远程脚本与字体；开发 CSP 单独保留 Vite HMR 所需连接。Tauri capability 只新增 dialog、updater、process 的必要权限，以及保存命令的调用；不授予宽泛文件系统访问。

**外部前置条件。** 自动更新依赖当前源码仓库公开可见，以及 CI secrets：Tauri updater 私钥与私钥密码。签名密钥对需由维护者生成一次，公钥写入 `tauri.conf.json`，私钥只存 CI。公开仓库应当开启分支保护、secret scanning，并限制 tag 推送权限，避免未授权发布。缺少这些前置条件时，除发布与真实更新验证外的工作仍可独立完成；首次可用自动更新的版本为 `0.2.0`。

当前仓库没有其他 Spec，本规范不涉及跨 Spec 接口或并行实现依赖。

### 核心决策

- **草稿使用 IndexedDB，并拆分文本与照片**：容量和异步能力优于约 5MB 的 localStorage，拆分后避免每次输入重写大图。备选 localStorage 被放弃，因为图片会迅速触顶且阻塞主线程。
- **恢复完成前不初始化、不持久化**：用 hydration gate 取代“空数据就写默认值”的隐式逻辑，避免启动时默认值覆盖草稿。备选“先渲染默认值再异步替换”被放弃，因为会产生闪烁和覆盖风险。
- **原生保存使用 dialog 插件 + 窄职责 Rust 命令**：只写用户选中的文件，避免 `fs` 插件为覆盖任意保存位置而授予宽泛目录权限。备选“直接用 fs 插件 + `$HOME/**` 作用域”被放弃，权限面过大。
- **字体改用系统字体栈**：移除远程字体请求，满足离线与国内网络环境；接受 Windows（微软雅黑）与 macOS（苹方）字形差异。备选“本地打包 Noto Sans SC”被放弃，因为会增加数 MB 安装包体积。
- **公开源码仓库直接托管更新产物**：当前源码仓库将公开，Tauri updater 可以匿名读取其 Release；无需独立 releases 仓库、跨仓库令牌或镜像步骤。备选“保持源码私有 + 独立公开 releases 仓库”需要镜像和额外 PAT；备选“外部对象存储”需要域名与凭据。
- **采用确定性字段上限 + CSS 字号分级**：在输入层限制长度，在模板层按长度分级缩小字号，行为可测试、导出可预测。备选“运行时测量并自动缩放任意长度”被放弃，因为实现复杂且跨平台字体度量不稳定。
- **版本基线设为 `0.2.0`，版本源统一校验**：一次发布同时承载 P0–P2 修复和首个 updater 产物。备选继续使用 `0.0.0`/`0.1.0` 会造成标签、安装包和更新清单不一致。
- **测试采用 Vitest + Testing Library + Playwright，Tauri 专属流程手工验证**：自动化覆盖可稳定复现的逻辑与浏览器流程；原生对话框、文件写入和更新安装由发布前手工清单验证，避免引入不稳定的桌面 E2E 基础设施。
- **收紧生产 CSP**：移除 `csp: null`，只允许本地资源和必要的 IPC；更新网络请求由 Rust 侧发起，不扩大页面网络权限。

## 风险与否定性保证

- **风险评估：高。** 本规范引入自动更新与签名私钥处理、原生文件写入、持久化数据 schema，以及公开源码仓库，影响面超出局部 UI 修复。关键操作包括：生成和配置 updater 签名私钥；将源码仓库改为公开；向公开仓库发布安装包与 `latest.json`；应用内下载、安装并重启；向用户选择的路径写入或覆盖文件；错误兜底中的“清除当前草稿”。这些操作需要按审批策略单独确认，不能仅凭 Spec 批准自动执行。
- **更新链路风险**：错误签名、错误更新源或被篡改的 `latest.json` 可能导致安装恶意代码。通过验收标准 10.4、10.8、10.9 的签名校验、HTTPS、私钥隔离和公开清单约束降低；发布前需验证无效签名会被拒绝。
- **首次升级断层**：`0.1.0` 没有 updater，现有用户必须手动安装一次 `0.2.0`。发布说明必须明确该限制；不能宣称旧版本会自动升级。
- **持久化与数据边界**：升级不得改变 `com.sawyerlau.onlyu`，否则 IndexedDB 会换域并表现为草稿丢失。草稿损坏或 schema 不支持时按验收标准 1.4 回退默认值并提示；配额不足时按 1.5 保留内存数据。
- **导出文件安全**：原生保存只写用户在对话框中选择的路径；临时文件 + 替换策略确保写入失败不破坏已有同名文件（验收标准 4.4）。不得为了便利开放任意目录读写。
- **公开源码风险**：源码、提交历史和品牌素材会公开；通过不提交密钥、开启 secret scanning、分支保护和限制 tag 推送权限降低风险。公开仓库的 Release 只承载安装包、签名和更新清单。
- **隐私与网络边界**：草稿、照片和表单内容不离开本机；除启动/手动更新检查外，应用不发起业务网络请求；更新检查只发送版本与平台等必要信息。字体、图片和导出均不依赖远程服务。
- **否定性保证（Invariants）**：
  - 不实现联系方式/二维码、模板选择器、照片拖拽、批量生成等范围外产品功能。
  - 不发布 macOS/Linux 安装包，不接入 Windows 代码签名，不实现更新回滚或遥测。
  - 不在仓库、日志或安装包中出现 updater 私钥。
  - 不在未通过签名校验或用户确认的情况下安装更新。
  - 不授予 `fs` 插件的宽泛目录权限，不写入用户未选择的路径。
  - 签名私钥不得进入公开仓库、日志或 Release 产物。
  - 不改变现有海报视觉方向；只做排版边界、字体回退与可靠性修复。
